# Code map

Architecture notes that don't change often. For the current file list with each file's purpose and exports, run:

```
python3 scripts/codemap.py            # whole repo (generated live, never stale)
python3 scripts/codemap.py web/src    # one area
```

## Data flow (SPEC §6, §16)
```
camera ─► capture.py ─► capture records (JSONL, contracts.CaptureFrame)
                           │   (same stream for live, fallback, tests/scenarios)
                           ▼
          recogniser.py ─► StepEvent  ──(low confidence)──► verifier (Gemini, behind fake)
                           ▼
          tasks/graph.py (task graph data) + errors.py + hesitation.py ─► TaskError
                           ▼
          scoring.py ─► session score ─► change_detection.py (+ feedback.py thresholds) ─► flag
                           │                      drift.py ─► slow-drift trend (not an alert)
                           ▼
          patterns.py: extract_features ─► score_patterns (patterns_library.py, as data)
                           │                  ─► ranked PatternMatch ("consistent with …")
                           ▼
          alerts.py + checks.py + explain.py ─► Alert ─► api.py (REST + live.py WebSocket) ─► web/
```

## Where things live
- `web/src/ui/charts/` — dependency-free SVG `LineChart` (time/value points, optional usual-range band and comparison, summary and keyboard exploration), controlled `RangeSelector` on `SegmentedControl`, and shared linear/time scales with readable ticks. Styles use the chart tokens in `index.css`.
- `deploy/` packages the API and nginx dashboard for Docker hosts. `docker-compose.yml` defaults to the offline demo with a named replay/cache volume and an optional `tsdb` profile; `check.sh` builds the stack, checks container permissions/CORS/SPA routing, runs `scripts/smoke.sh`, and tears down its test volumes. Setup and TLS guidance: `docs/DEPLOY.md`.
- Contracts — source of truth is the pydantic models in `pipeline/src/routine_watch/contracts.py`; `contracts/*.schema.json` and `web/src/contracts.ts` are generated (`cd pipeline && uv run python -m routine_watch.contracts`). Never hand-edit generated files. Heavy tasks only. `CONTRACTS` are the records; `PROTOCOLS` are a socket's messages — `contracts/live_message.schema.json` is `/ws/live`'s `oneOf` on `type` (schema only, no TS: the dashboard has its own union in `web/src/live/useLiveSession.ts`, and `pipeline/tests/test_live_contract.py` validates a replayed session against the schema and fails if the two sides list different messages).
- `pipeline/src/routine_watch/` — one module per stage. `scenario.py` is the scenario file format (`tests/scenarios/<name>/expected.yaml` + `frames.jsonl`/`steps.jsonl`, as pydantic models, `load_scenario`); `replay.py` runs a loaded scenario through the whole pipeline offline and compares it with its `expected.yaml`, re-exporting `scenario.py`'s names so existing `from .replay import ...` keeps working. `demo.py` and `synth/` make synthetic residents, history and care records.
- `patterns.py` + `pattern_features.py` + `patterns_library.py` — from a flag to likely patterns (SPEC §7.5). `pattern_features.extract_features` reads one resident's own sessions and care records into `Features` (error rates by type against their own baseline, onset in days or weeks from `change_detection` and `drift`, time of day, durations, care-record context); `patterns.score_patterns` ranks the library against those features and fills `Alert.patterns`. `patterns.py` re-exports `extract_features` and `Features` so callers only need the one module. The library is data — signals and weights, time profile, checks, urgency, citation — so a new pattern is a new entry and no code change. Features the pipeline does not record yet (step gaps, movement speed, per-hand shares) stay `None`, and a pattern whose signals are mostly unmeasurable is not scored at all. `score_patterns(weights=..., answers=...)` multiplies each confidence by this resident's nurse-feedback weight for that pattern before the threshold and the sort, and says so in the evidence (SPEC Nice to have 8). Deterministic: same features and same past answers, same patterns; the LLM summariser never adds one.
- `pipeline/src/routine_watch/api.py` — FastAPI app setup, `/health`, `/demo/reset` and `GET /handoff` (`handoff.py`). `api_cache.py` guards every paid API call (`LIVE_API`).
- `pipeline/src/routine_watch/api_state.py` — the feedback store (`_feedback_store`, `FeedbackStore`) and the feedback-tuned helpers built on it (`_tuned`, `_SUMMARY_FIELDS`, `_flagged_residents`), shared by `api.py`, `api_alerts.py` and `api_residents.py`. No FastAPI app import, so it carries no risk of the circular `from . import api` reach-back those two routers used to need; every importer takes a module-level `from . import api_state` instead, and a reset (`/demo/reset`, test fixtures) calls `api_state.reset()`, which mutates `_feedback_store` in place rather than rebinding the module global, so every earlier import of it still sees the reset.
- `pipeline/src/routine_watch/api_live.py` — the per-room monitoring switch (SPEC §12: `GET /monitoring`, `PUT /rooms/{room}/monitoring`, `GET /rooms/{room}/monitoring/history`) and WebSocket `/ws/live` (`live.py`), as an `APIRouter` `api.py` includes. Both turn on the same room-pause state (`monitoring.get_monitoring_store`), which is why they live together instead of in `api.py`. The switch also logs who paused or resumed a room and when (`MonitoringStore.history`, newest first, last 20): `web/src/resident/MonitoringHistory.tsx` shows the last five under the switch on resident detail, and `/demo/reset` clears the trail with the pauses.
- `pipeline/src/routine_watch/api_alerts.py` — `/alerts[/{id}]` and `POST /alerts/{id}/feedback`, as an `APIRouter` `api.py` includes. `AlertFeedbackIn`, `KNOWN_CAUSES` and `OTHER_CAUSE` are re-exported from `api.py` so existing imports keep working. Reads `api_state._feedback_store` and `api_state._flagged_residents()` (shared with `/residents` and `/handoff`).
- `pipeline/src/routine_watch/api_residents.py` — `/residents[/{id}]`, `GET /residents/{id}/drift` (daily score trend from `drift.drift`, backs the drift card), `GET /residents/{id}/feedback` (what her nurses answered, newest first, plus the pattern weights and names those answers moved - backs the "What nurses said" card), `GET /patterns` (the pattern library, read-only), `GET /sessions/{id}/replay` and `GET /residents/{id}/normal_replay` (skeleton evidence, `evidence.py`), as an `APIRouter` `api.py` includes. Reads `api_state._SUMMARY_FIELDS` and `api_state._tuned` (shared with `/alerts` and `/handoff`).
- `pipeline/src/routine_watch/evidence.py` — skeleton-only replay for an alert's "open evidence" view (never video, SPEC §8). Every alert replays `tests/scenarios/tea_no_kettle`, with a `tea_normal` ghost layer for comparison, until a real recording of the demo's actual bad session exists.
- `pipeline/src/routine_watch/stick_figure.py` — the stand-in body for frames nobody filmed: `reaching_for(point)` / `reaching_into(box)` give one made-up `Pose` + `HandLandmarks` reaching there. `live._synthetic_frames` (a scenario written at step level) and `evidence.py` (recordings written as boxes only) both fill their `poses`/`hands` from it, so the live skeleton view and the ghost replay have a body to draw. Real capture never comes through here.
- `pipeline/src/routine_watch/feedback.py` — `FeedbackStore` nudges a resident's alert threshold on nurse feedback (false alarm raises it, confirmed lowers it) and records a per-alert `cause` plus the pattern the alert led with, so `cause_counts` tallies confirmed causes and `pattern_weights` / `pattern_answers` turn them into that resident's pattern weights (0.7-1.3, one answer worth 0.1) for `build_alerts(residents, feedback=store)`.
- `web/src/alert/TimeOfDayStrip.tsx` — the alert's errors per part of the day (morning / afternoon / evening) over the last 14 days, under the error list: the visible evidence behind the evening-only worsening pattern (SPEC §7.5), which `patterns.py` otherwise only states in words. Fed by the optional `errors_by_time_of_day` on the alert payload, which `api_alerts.errors_by_time_of_day` reads off the resident's own sessions at the route (not stored on the `Alert` record); the strip is hidden when that field is null, as it is offline.
- `web/src/alert/FeedbackButtons.tsx` — once confirmed, offers the alert's patterns + "other" in the optional "What was it?" picker.
  The selection travels as `cause` in `POST /alerts/{id}/feedback`; `api.py` validates it against `KNOWN_CAUSES` (pattern ids + "other", otherwise 422).
  The API passes the accepted value to `FeedbackStore.record(..., cause=)`.
- `pipeline/src/routine_watch/live.py` — `session_messages` sends one push alert via `notify.get_notifier()` exactly when a session's end flips a resident from unflagged to flagged (`_resident_flagged`, read from `demo_residents()` before and after `_record`), not per session.
- `pipeline/src/routine_watch/notify.py` — `get_notifier` returns `FakeNotifier` unless `LIVE_API=1` and both `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` are set, so no test/CI/replay run ever sends a real push.
- `pipeline/src/routine_watch/alerts.py` — `task_errors` returns the errors a live session was recorded with when the session has them (`demo._live_sessions` carries `error_events` out of `session_log`), and otherwise invents a plausible step and timestamp per error from a session's error-type *counts* only (synthetic history has no per-instance step events), spreading them evenly over the session duration; `distinct_clauses` then drops any error whose type/step/displayed-minute exactly repeats an earlier one so the explainer summary never shows a duplicate clause, and the summary's "this session" becomes "across N sessions" when the flag rests on more than one (`explain.scope_phrase`).
- `scripts/smoke.sh` — hits every API route (including `/alerts`, drift and feedback) and the dashboard against a running `scripts/dev.sh up` stack; first plays mrs-k's `tea_skip_teabag_pour_twice` live session so there's a flagged resident, then prints PASS/FAIL per check. Never sets `LIVE_API`, never POSTs feedback.
- The live view has two sources of the same messages: `live.py` replays a recorded scenario (the demo's fallback), `live_camera.py` reads a live capture stream as it arrives. Same message types, same order, so the dashboard cannot tell them apart. `/ws/live` picks between them: `?scenario=` (the default) or `?source=camera`, which reads `capture.camera_frames` on a background thread (`live_camera.frames_in_thread`).
- `demo._top_pattern` fills the `top_pattern` field on `GET /residents` for watch/flagged residents only (the best pattern their change is consistent with); `web/src/overview/UnitOverview.tsx` shows it on the unit overview.
- `web/src/live/LiveScreen.tsx` wraps `LiveSession` with a tea/medication routine picker, so the demo can start a live session for either routine.
- `handoff.py` — the shift handoff (`GET /handoff?hours=`): per resident, how many sessions in the window had a change flagged for review, how many alerts nobody has given a verdict on yet, and whether `drift.py` sees a slow rise, plus one summary from `explain.py`'s `Explainer`. Windows end at `demo.DEMO_NOW`, the clock the demo's history and its live session share.
  It builds that summary from the same evidence as the resident's alert, not a re-synthesised copy: `alerts.session_id_for`, `alerts.task_errors` and `alerts.distinct_clauses` give it the same session ids, error events and deduplicated clauses the alert shows, and `alerts.normal_error_rate` is the same baseline the alert measures against - so a nurse reading the handoff and then opening the alert sees the same steps, times and baseline, never a different set.
  On the dashboard, a handoff row opens that resident's alert by looking up her id in `GET /alerts` (`web/src/handoff/Handoff.tsx`'s `alertByResident`, SPEC §9 / T152).
  Each row also carries `previous_flags`, the same count for the window before this one (`[now - 2 x hours, now - hours)`, same resident, same feedback-tuned bar), so a nurse reads better or worse rather than a bare number. The current window owns the instant they share, so a session at `now - hours` is counted once.
  And `unclear_sessions`: how many sessions in that resident's **room** the capture was too unclear to score in the window (`session_log.unclear_in`, T355). Those sessions are in nobody's history by design (T342), so without the count a blocked or badly lit camera reads as a quiet room; `web/src/handoff/Handoff.tsx`'s `unclearLabel` turns it into one grey chip and one line of the copied handoff ("2 sessions too unclear to score - check the camera view"), about the camera view and never about the resident.
- `web/src/handoff/HandoffDelta.tsx` — the "up / down / same vs last shift" indicator for one handoff row, from that row's `flags` and `previous_flags`: one phrase ("2 more than last shift", "Nothing flagged either shift"), with the arrow and the colour as second signals only. Renders nothing when the payload sent no `previous_flags`. `Handoff.tsx` renders it in every row, beside the chips that count the sessions it compares, and `handoffDeltaLabel` gives the same phrase to the copied handoff line so the row and a note pasted from it can't drift apart (T350).
- `session_log.py` — the sessions this process has watched finish, in memory. `live.py` records one when a session ends (against the demo resident unless told otherwise); `demo.py` merges a resident's recorded sessions into their history, which is how a live session spikes their sparkline and counts toward their flag (SPEC §10 step 4). Same shape as `store.py`, which replaces it once a database is wired up. It also keeps the sessions that became nobody's: `record_unclear`/`unclear_in` tally, per room and as timestamps only, the sessions too unclear to score that `live.py` leaves out of the history (T342), which is what the handoff's `unclear_sessions` reads. It is global state: a test that plays a live session must `session_log.reset()`.
- `explain_claude.py` (`get_explainer()`) and `verifier.py` (`get_verifier()`) each default to an offline fake (`TemplateExplainer`, `FakeVerifier`); they only build the real client when `LIVE_API=1` and the matching key (`ANTHROPIC_API_KEY` / `GEMINI_API_KEY`) is set. Both route real calls through `api_cache.cached_call` and take their model from an env var (`ANTHROPIC_MODEL`, `GEMINI_MODEL`), falling back to the cheapest default otherwise.
- `web/src/` — one folder per screen (SPEC §9): `overview/`, `resident/`, `live/`, `alert/`, `evidence/`, `about/`, `handoff/`. Each has its own `api.ts` with an offline mock fallback, from `mock/` or from the screen's own folder (`live/mockLiveStream.ts`, `handoff/mockHandoff.ts`).
- `web/src/ui/` + `web/src/index.css` — the design system (tokens, Card, StatusChip, Pill, SegmentedControl, Row, Button, SectionHeader, states). Use these; don't restyle per screen. The brief behind them — principles, the token table, chart rules, status mapping, do/don't and the Fey reference links — is `docs/DESIGN.md` (T401). `web/src/ui/tokens.test.ts` parses `:root` out of `index.css` and fails if any text token drops below 4.5:1 on a surface or inside a tinted pill, so a new colour has to clear contrast before it ships. The pre-T401 token names (`--bg`, `--panel`, `--border`, `--muted`, `--alarm`, `--error-*`) are aliases of the new ones so screens keep working until their own redesign task; don't add new uses.
- `web/landing.html` + `web/src/landing/` — the public one-pager for the demo URL (what it is, why it matters, how it works, the pattern wording, privacy, the stack), its own Vite entry alongside `web/index.html` (`build.rollupOptions.input` in `web/vite.config.ts`, output `dist/landing.html`). It renders on its own, with no API calls and no dashboard code, so changing it can't break the demo path; it shares only `web/src/index.css`'s tokens and `.btn`/`.card` classes. Copy stays under ~350 words, and its test checks that (T378).
- `tests/scenarios/` — end-to-end cases (`expected.yaml` + `frames.jsonl` or `steps.jsonl`), run by `scripts/e2e.sh`.
- `scripts/` — `ci.sh` (CI), `dev.sh` (local stack), `camera.sh` (local stack on a real webcam), `e2e.sh`, `codemap.py`, plus agent tooling `tasks.py`, `worker.sh`.
- `prompts/` — agent prompts; `prompts/areas/` guides attached per task area.

## Adding things
- New pipeline stage or rule → its own module, pure functions, a unit test, and a scenario if behaviour changes.
- New screen → new folder under `web/src/`, built from `web/src/ui/`, with mock data and loading/empty/error states.
- New public page (not a nurse screen) → its own Vite entry + folder, like `web/landing.html` and `web/src/landing/`.
- New shared shape → `contracts.py` first (heavy task), then regenerate schemas + TS.
